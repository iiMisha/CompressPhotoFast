# Commit

По умолчанию **и коммитит, и сразу пушит** в `origin` одной операцией — без отдельного подтверждения пуша. Сообщение генерируется на русском по Conventional Commits (стиль проекта RogaineHelper). Пуш — обязательная часть, если пользователь явно не попросил «только закоммитить, без пуша».

## Формат сообщения

```
<type>(<scope>): <краткое описание в одну строку>

<необязательное тело — что и зачем, списком>
```

### Type (ровно один)

- `feat` — новый функционал или заметное расширение существующего
- `fix` — исправление бага, некорректного поведения
- `refactor` — переработка кода без изменения внешнего поведения
- `perf` — улучшение производительности
- `docs` — только документация (AGENTS.md, README, комментарии, changelog)
- `style` — форматирование, отступы, переименование без изменения логики
- `test` — добавление/правка тестов
- `build` — сборка, зависимости, Gradle, версии
- `ci` — CI/CD, скрипты
- `chore` — рутинные задачи, не влияющие на код продукта

### Scope (необязателен)

Область изменения из контекста проекта: `json`, `optimization`, `yandex-disk`, `export`, `storage`, `map`, `test`, `AGENTS`, `large-files` и т.п. Если изменения затрагивают несколько модулей без доминирующего — scope опускается.

### Правила описания (строка type)

- На русском языке
- Стартует с глагола в совершенном виде в прошедшем времени или инфинитиве (`добавлен`, `исправлена`, `вынесено`, `обновлён` ...), единый стиль со историей `git log`
- lowercase, без точки в конце
- ≤72 символов ideally; если короче не получается — переносим суть в тело
- Без_water_stampов («обновлён файл X») — про суть изменения, а не про файл

### Тело (необязательно)

Добавлять, когда: фиксят нетривиальный баг, затрагивают несколько модулей, вводят инвариант. Формат — маркированный список `-` с конкретикой (что изменено, почему, ключевые имена классов/методов). Без воды.

### Примеры (из реальной истории)

- `feat(json): add data corruption recovery and integrity notifications`
- `fix(optimization): устранена проблема с ожиданием routeMetrics и дубликатами`
- `refactor(large-files): вынесение логики работы с крупными файлами в отдельные контроллеры`
- `docs(AGENTS): добавлена документация о Hilt‑интеграционных тестах`
- `feat(yandex-disk): добавлена контент-адресуемая синхронизация карт\n - computeLocalImageIndex, computeJsonChecksums в BackupSerializer\n - ContentAddressedSyncPlan + тесты`

## Workflow

### 1. Собрать контекст изменений

```bash
git status
git diff            # unstaged
git diff --staged   # staged
git log -5 --pretty=format:"%s"   # стиль недавних коммитов
```

Если diff большой — читать по файлам/чанкам через `git diff -- <path>` или инструмент Read.

### 2. Решить: один коммит или несколько

**Несколько коммитов**, если изменения логически независимы (напр.: bugfix + несвязанный refactor + обновление AGENTS.md). Стейджить файлы по группам (`git add <path1> <path2>`) и коммитить отдельно.

**Один коммит**, если изменения образуют связанную единицу работы.

Не смешивать `docs`/`chore` с `feat`/`fix` в одном коммите без необходимости.

### 3. Сформировать сообщение

По diff определить:
1. **type** — что это по сути (новое/фикс/рефакторинг/...)
2. **scope** — затронутая область
3. **описание** — суть изменения
4. **тело** — если нужно

### 4. Сразу коммит и пуш (одной операцией)

Коммит и пуш выполняются **всегда вместе, без паузы на подтверждение пуша**. Когда сообщение готово и сборка (если она нужна) зелёная — одной цепочкой:

```bash
git add <files> && \
git commit -m "<type>(<scope>): <описание>" -m "<тело если есть>" && \
git push origin HEAD        # пушит текущую ветку; origin уже настроен
```

`&&` гарантирует, что пушится только успешно созданный коммит.

#### Особые случаи

- **Нет upstream у текущей ветки**: `git push -u origin HEAD`.
- **Защищённая/прод-ветка**: пуш в текущую локальную ветку RogaineHelper (`origin HEAD`) делается по умолчанию без уточнения. Уточнять у пользователя только при явном пуше в защищённую ветку чужого/публичного репо.
- **Конфликтующие имена / длинные пути**: стейджить по явным путям.
- **Пользователь явно попросил «без пуша»**: сделать только коммит, не пушить.

### 5. Отчёт пользователю

Кратко: что закоммичено (type+scope+описание), сколько файлов, ссылка на коммит/хэш, подтверждение пуша. Без избыточного пересказа diff.

## Важные оговорки

- **Не коммитить автоматически генерируемые артефакты** (`.skill`, `build/`, `__pycache__/`) — проверь `git status` и стейджь только источники.
- **Перед пушем — сборка обязательна**, если изменён код продукта (правило проекта: `./gradlew :<module>:assembleDebug` или `./gradlew assembleDebug`). Если пользователь явно не просил пропустить сборку — собрать и убедиться, что зелёная. При падении — НЕ пушить, доложить.
- **Не подменять сообщения пользователя**: если пользователь дал готовое сообщение — использовать его дословно, только проверить соответствие формату и при необходимости спросить.
- **Не делать `--amend`/force-push без явного запроса**.
- **Секреты**: если в diff замечены токены/ключи/`yandex_token`/пути с кредами — остановить и предупредить до коммита.
