# Единое уведомление автосжатия и статистики

## Контекст и решения

- Сейчас foreground-служба показывает постоянное уведомление через `NOTIFICATION_ID_BACKGROUND_SERVICE` (`2`), а `ImageCompressionWorker` после каждого успешного результата создаёт второе тихое уведомление статистики с ID `10` и отдельным каналом.
- Единым остаётся foreground-уведомление автосжатия: оно сохраняет `ongoing`-статус, переход в приложение и действие «Остановить».
- Пока в локальных текущих сутках нет успешных сжатий, уведомление содержит существующее описание мониторинга. После успеха оно обновляется тем же ID и показывает число сжатых фото, размеры до/после и экономию в развёрнутом тексте.
- При перезапуске службы в тот же день уведомление сразу строится из сохранённого `StatsTracker.getDailyCompressionStats`, чтобы статистика не исчезала до следующего сжатия.
- Отдельный таймер сброса на полуночь не добавляется. Статистика обнуляется по существующей логике при первом успешном сжатии новых локальных суток; до этого сохраняется стандартный текст мониторинга при новом запуске службы.
- Для обновлений со старых версий нужно отменить активное устаревшее уведомление ID `10` при создании единого служебного уведомления. Старый канал Android удалять программно не нужно: системные каналы и пользовательские настройки для них не следует трогать.

## Изменения

1. В `app/src/main/java/com/compressphotofast/util/Constants.kt` удалить идентификатор отдельного канала суточной статистики и ID сводки, которые больше не используются. Оставить ID foreground-службы единственной точкой публикации объединённого состояния.
2. В `app/src/main/java/com/compressphotofast/util/NotificationUtil.kt` удалить создание канала `daily_compression_stats_channel` и отдельный метод `showDailyCompressionNotification`.
3. В `NotificationUtil` централизовать построение уведомления мониторинга с необязательной `DailyCompressionStats`:
   - всегда использовать основной канал и ID foreground-службы;
   - при наличии статистики добавлять компактную строку и `BigTextStyle` с размерами и экономией, используя существующие строки статистики;
   - сохранять низкий приоритет, постоянность, `PendingIntent` открытия приложения и действие остановки;
   - сделать обновления от worker бесшумными и с `setOnlyAlertOnce`, чтобы каждое фото не вызывало новый сигнал;
   - отменять устаревшее уведомление ID `10` как миграционную очистку перед публикацией объединённого уведомления.
4. В `NotificationUtil` добавить/адаптировать публичный метод обновления уведомления мониторинга со статистикой: он проверяет доступность обычных уведомлений, строит тот же foreground-формат и вызывает `NotificationManager.notify(Constants.NOTIFICATION_ID_BACKGROUND_SERVICE, ...)`. Он не должен запускать или останавливать службу.
5. В `createBackgroundServiceNotification` получать актуальную статистику текущих суток из `StatsTracker` и передавать её в общий построитель. Таким образом `BackgroundMonitoringService.startForegroundWithNotification()` не меняет контракт запуска foreground-службы, но восстанавливает текст статистики после перезапуска.
6. В `app/src/main/java/com/compressphotofast/worker/ImageCompressionWorker.kt` после успешного сохранения и записи статистики вызывать обновление объединённого уведомления вместо публикации отдельной суточной сводки. Не менять порядок: обновлять только после проверки сохранённого файла и успешной записи статистики.
7. В `app/src/main/res/values/strings.xml` удалить строки имени и описания неиспользуемого отдельного канала. Сохранить строки форматирования статистики; добавить новую строку только если для компактной строки объединённого уведомления нельзя корректно использовать существующие ресурсы.
8. Обновить `app/src/test/java/com/compressphotofast/util/NotificationUtilTest.kt`:
   - проверять, что статистика обновляет уведомление с ID `NOTIFICATION_ID_BACKGROUND_SERVICE`, а не создаёт сводку с отдельным ID/каналом;
   - проверять заголовок состояния автосжатия, текст с экономией, низкий приоритет, `FLAG_ONGOING` и `FLAG_ONLY_ALERT_ONCE` для обновления;
   - проверить замену данных при втором успешном сжатии и отмену заранее созданного legacy-уведомления ID `10`.
9. Удалить или скорректировать проверки констант в `ConstantsTest.kt`, относящиеся к удалённым константам. После реализации обновить краткий актуальный контекст в `AGENTS.md` через навык `agents-updater`.

## Границы и риски

- Не меняются каналы и уведомления обработки WorkManager, результатов отдельных сжатий, ошибок и пакетной обработки.
- Foreground-служба должна всегда получить уведомление даже при недоступном `POST_NOTIFICATIONS`; проверка доступности применяется только к обычному обновлению из worker, как и в существующей статистике.
- Обновление статистики не должно заменять или удалять foreground-уведомление ID `2` без действия остановки, иначе пользователь потеряет управление службой.

## Проверка

1. Запустить `./gradlew assembleDebug`.
2. Запустить Android unit-тесты через навык `android-test-suite` (`./gradlew testDebugUnitTest`).
3. Из-за изменения уведомления фоновой службы выполнить интеграционную проверку на API 29+ и API 34+: включить автосжатие, убедиться в одном persistent-уведомлении с кнопкой остановки, успешно сжать две фотографии и проверить обновление счётчика/экономии без второго уведомления; перезапустить службу и проверить восстановление статистики текущих суток.
4. Запустить instrumentation-набор через навык `android-test-suite`, если доступен эмулятор, поскольку затронут foreground service и реальная доставка уведомлений.
