# Фикс «битых» фото при массовом сжатии в режиме замены

## Симптом

Huawei P60 Pro, Android 12, галерея Huawei: после массового сжатия часть фото при каждом
открытии первые секунды показывается с серыми/зелёными квадратами и полосами, затем
отрисовывается корректно. В галерее Яндекс.Диска файлы корректны всегда.

## Диагноз

Файл на диске валиден (в чужом вьювере декодируется корректно). Битым выглядит только
первый кадр в галерее Huawei — это её кэш миниатюр (thumbnail).

Цепочка возникновения:

1. В replace-режиме (`MediaStoreUtil.saveCompressedImageFromStreamInternal`, MediaStoreUtil.kt:479-579)
   существующий файл перезаписывается на месте через `openFileDescriptor(uri, "rwt")`.
   Файл всё это время виден в галерее (IS_PENDING=0). Между truncate и завершением
   записи + fsync существует окно в секунды, когда видимый файл усечён/частичен.
2. При массовом сжатии MediaStore рассылает change-уведомления; галерея Huawei (или
   MediaStore thumbnails provider) успевает сгенерировать миниатюру из частично
   записанного файла и кэширует её.
3. Инвалидации кэша не происходит, потому что после EXIF-записи приложение
   **восстанавливает исходную дату модификации**
   (`ExifUtil.applyExifFromMemory`, ExifUtil.kt:899-902 → `MediaStoreDateUtil.restoreModifiedDate`).
   Кэши миниатюр ключуются на (id, date_modified): дата совпадает со старой → кэш
   считается валидным → битая миниатюра живёт вечно и показывается первой при каждом
   открытии, пока полный decode не заменит её на экране.

## Задачи

1. **Прекратить «обнулять» изменение файла для кэшей миниатюр.**
   - В `ExifUtil.applyExifFromMemory` после успешного `saveAttributes()` не
     восстанавливать старую `date_modified` (или восстановить её только для
     EXIF-полей, но в MediaStore записать актуальное время файла).
   - `MediaStoreDateUtil.restoreModifiedDate` оставить для mode «сохранение в отдельную
     папку», в replace-режиме пропускать; вместо него убедиться, что MediaStore видит
     обновлённую дату (после перезаписи вызвать update с DATE_MODIFIED = время записи
     или положиться на автообновление MediaProvider).
   - Аналогично проверить CLI (`compressphotofast-cli/src/cli.py`, `compression.py`) на
     семантическое соответствие.

2. **Сократить окно «виден частичный файл» (defense-in-depth, опционально).**
   - Оценить установку IS_PENDING=1 на время перезаписи существующего URI в
     `saveCompressedImageFromStreamInternal` и снятие после fsync + верификации.
     Риск: не все OEM-галереи корректно скрывают pending-файлы, и пользователь может
     временно «потерять» фото — пометить как экспериментальный этап за флагом в
     `SettingsManager`, по умолчанию выключен.

3. **Диагностика (в той же итерации).**
   - Логировать в replace-пути время между truncate и завершением fsync
     (`LogUtil.processInfo`), чтобы оценить реальное окно.

## Не входит в объём

- Изменение инвариантов сжатия (100 КБ / 30% / 10 КБ).
- Удаление backup/restore механизмов — они остаются как есть.

## Валидация

1. `./gradlew assembleDebug`.
2. Unit-тесты через навык `android-test-suite` (`testDebugUnitTest`).
3. Ручная проверка на Huawei P60 Pro (Android 12):
   - сжать батч в режиме замены;
   - открыть ранее «битые» фото в галерее Huawei несколько раз подряд — первый кадр
     должен быть корректным (миниатюра перегенерирована благодаря новой date_modified);
   - убедиться, что в галерее Яндекс.Диска ничего не регрессировало;
   - убедиться, что маркер `CompressPhotoFast_Compressed` в EXIF сохраняется и
     повторное сжатие по-прежнему отсекается проверкой эффективности.
