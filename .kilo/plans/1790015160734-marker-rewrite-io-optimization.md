# Оптимизация I/O фазы 2 записи маркера сжатия (ExifUtil)

## Цель
Сократить дисковый I/O итеративной записи размера в EXIF-маркер без изменения внешнего поведения и инвариантов.

## Контекст
`rewriteMarkerWithActualSize` (ExifUtil.kt, строки ~1079-1121) делает до 3 попыток записи размера. Каждая попытка через `writeMarkerWithSize` (строки ~1129-1197):
- копирует **весь файл** в backup (`openInputStream` + `copyTo`, ~0.6–1 МБ на копию);
- вызывает `saveAttributes()`;
- прогоняет `verifyImageIntegrity` (открытие потока + декодирование заголовков).

В типичном сценарии сходимость с 1-й попытки, но backup+verify выполняются всегда; в ретрае копия файла делается повторно до 3 раз. `writeMarkerWithSize` используется только внутри `rewriteMarkerWithActualSize` — можно менять сигнатуру свободно.

## Решения (согласованы с пользователем)
1. Backup создаётся один раз на весь цикл попыток, а не на каждую попытку.
2. `verifyImageIntegrity` выполняется только на финальной записи (сходимость или деградационная заглушка), а не на промежуточных попытках, которые всё равно будут перезаписаны.

## Изменения

### ExifUtil.kt
1. **`rewriteMarkerWithActualSize`**:
   - Перед циклом: создать backup один раз (копирование файла + `BackupRegistry.registerBackup`), как это сейчас делает `writeMarkerWithSize`. При неудаче создания backup — warning и `return false` (текущее поведение сохраняется).
   - Передавать backup в `writeMarkerWithSize(..., backupFile, verify: Boolean)`.
   - Политика верификации: `verify = true`, если (запись сошлась по размеру) или (последняя попытка) или (деградационная запись заглушки). При расхождении размера с оставшимися попытками — `verify = false` (файл будет перезаписан; если он повреждён, следующий `saveAttributes()` упадёт → restore из backup → выход с false).
   - Backup удаляется и `BackupRegistry.clearBackup` вызывается в `finally` блока, охватывающего весь цикл (включая деградацию).
2. **`writeMarkerWithSize`**: новая сигнатура с параметрами `backupFile: File` и `verify: Boolean`. Убирает собственное создание/удаление backup; restore-логика и финальная верификация (если `verify = true`) сохраняются без изменений.
3. Комментарии KDoc обновить: одна копия backup на цикл, verify на финальной записи.

### Не меняется
- `getActualFileSizeOnDisk`, логика итераций, деградация на заглушку, restore из backup, `applyExifFromMemory` (пост-проверка остаётся — fstat дешёвый).
- Формат маркера, инварианты AGENTS.md, CLI (не затронут).

## Риски
- Промежуточная попытка повреждает файл без verify → следующая попытка падает в `saveAttributes()` → restore из единого backup → `return false` с последующей деградацией заглушкой в текущей схеме (restore уже возвращает false из rewrite — сверить: сбой записи → сразу false, заглушка не пишется; это соответствует текущему поведению `!writeOk → return false`).
-Robolectric: копирование/verify не меняются структурно, существующие тесты должны пройти без правок.

## Валидация
1. `./gradlew compileDebugKotlin` (сборка изменённого кода).
2. Unit-тесты `./gradlew testDebugUnitTest` через навык `android-test-suite` (CompressionMarkerSizeTest 9/9 и полный прогон).
3. `./gradlew assembleDebug`; после успешной сборки runtime-кода — опубликовать APK навыком `apk` (правило AGENTS.md).
4. Ручная проверка на устройстве: сжатие фото → в логе «✅ Размер файла ... (попытка 1/3)» единожды, backup-копий в логе/поведения нет на ретраях; reconciliation → ALREADY_COMPRESSED.
