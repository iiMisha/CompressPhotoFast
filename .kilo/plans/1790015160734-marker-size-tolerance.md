# Допуск по размеру маркера вместо итеративной записи

## Контекст и цель

Цикл «тестовое пересжатие → перезапись маркера» был вызван строгим сравнением размера файла со значением в маркере при недетерминированном дрейфе `ExifInterface.saveAttributes()` (до ~1 КБ). Текущее решение — итеративная запись `rewriteMarkerWithActualSize` с деградацией на заглушку. Пользователь выбрал более простой вариант: **допуск (tolerance) при сравнении + одна запись размера в фазе 2**, полный демонтаж итеративного механизма.

Решения (подтверждены пользователем):
- Вариант A: фаза 1 (маркер с заглушкой в общем `saveAttributes`) остаётся; фаза 2 — ровно одна запись размера + verify + backup/restore.
- Допуск: **4096 байт**, фиксированный (4-кратный запас над наблюдённым дрейфом ≤ ~1 КБ).

## Изменения

### 1. `Constants.kt`
Добавить публичную константу:
```kotlin
const val MARKER_SIZE_TOLERANCE_BYTES = 4096L
```

### 2. `ExifUtil.kt` — демонтаж итеративного механизма
- **Удалить**: `MARKER_SIZE_WRITE_ATTEMPTS`, цикл попыток, `FileSizeReading`/`stable`-флаг, early-degrade по потоковому чтению, финальную запись заглушки как отдельный путь.
- `readFileSizeFromDisk` упростить обратно до возврата `Long?` (каскад fstat → statSize → потоковый подсчёт остаётся; потоковый путь больше не «нестабильный», просто источник размера).
- `rewriteMarkerWithActualSize` → переименовать/упростить в `writeActualSizeMarker` (или сохранить имя):
  1. `createMarkerBackup` (одна копия, регистрация в BackupRegistry) — оставить как есть.
  2. Измерить размер (`getActualFileSizeOnDisk`).
  3. Одна запись через `writeMarkerWithSize(..., verify = true)` (параметр `verify` можно убрать — он всегда true).
  4. Пост-проверка: `|actual − written| > MARKER_SIZE_TOLERANCE_BYTES` → **одна** корректирующая перезапись с фактическим размером + verify; если снова вне допуска — только `LogUtil.error` (наблюдаемость), без дальнейших попыток. Так как строка маркера фиксированной ширины, вторая запись стабилизирована (на устройстве сходилась с 1-й попытки).
  5. `try/finally { clearBackup; delete }` — сохранить.
- Лог успеха: «✅ Размер файла X записан в маркер сжатия» (без «попытка N/3»).
- KDoc фазы 2 и `writeMarkerWithSize` переписать под новую семантику.
- **Пост-диагностика в `applyExifFromMemory` (строки ~978–984)**: сравнение `actualSize != marker.fileSize` заменить на допуск `abs(...) > Constants.MARKER_SIZE_TOLERANCE_BYTES`, иначе будут ложные ERROR-логи на законном дрейфе.

### 3. `ImageProcessingChecker.kt` — допуск в сравнении
Строка ~232:
```kotlin
val contentModified = markerFileSize != null && fileSize > 0L &&
    abs(fileSize - markerFileSize) > Constants.MARKER_SIZE_TOLERANCE_BYTES
```
Комментарий (строки ~224–229) обновить: расхождение в пределах допуска игнорируется (дрейф saveAttributes), большее — признак редактирования/пережатия. Парсер не меняется: `size: null` (заглушка/старый формат/HEIC) по-прежнему означает «пропустить» — это остаётся совместимостью со старыми файлами, но больше не генерируется новым кодом.

### 4. CLI — без изменений
Python-маркер формата `marker:quality:timestamp` (без поля размера) — сравнения размера в CLI нет, паритет не нарушен.

### 5. Тесты
- `CompressionMarkerSizeTest.kt`: удалить тесты цикла попыток/заглушки/early-degrade; обновить рефлексивные вызовы под новые сигнатуры (`Long?` вместо `FileSizeReading?`); добавить тест корректирующей перезаписи при дрейфе > допуска (мок/подмена размера).
- Добавить тесты чекера (если нет подходящего класса — в существующий тестовый набор `ImageProcessingChecker`): расхождение ≤ 4096 → `ALREADY_COMPRESSED`; > 4096 → `processingRequired = true`; `markerFileSize = null` → пропуск.

### 6. `AGENTS.md`
Обновить инвариант маркировки: «размер записывается одной записью в фазе 2 (заглушка → фактический размер, фиксированная ширина), проверка повторной обработки сравнивает размер с допуском `MARKER_SIZE_TOLERANCE_BYTES` = 4 КБ; mtime не используется».

## Порядок выполнения

1. `Constants.kt` — константа допуска.
2. `ExifUtil.kt` — упрощение фазы 2, удаление цикла/заглушки/stable-flag, допуск в пост-диагностике.
3. `ImageProcessingChecker.kt` — допуск в `contentModified`.
4. Тесты: правка `CompressionMarkerSizeTest` + новые тесты допуска чекера.
5. `./gradlew compileDebugKotlin`, затем полный `testDebugUnitTest` через навык `android-test-suite` (субагент).
6. `./gradlew assembleDebug` + публикация APK навыком `apk` (изменён runtime-код).

## Риски и границы

- **Слепая зона детекта правок**: изменение размера на ≤ 4 КБ не считается правкой. Приемлемо: реальные редактирования меняют размер на порядки больше.
- **Дрейф > 4 КБ** (экзотический EXIF): покрывается одной корректирующей перезаписью; если и она вне допуска — ERROR-лог, файл останется с маркером, чекер посчитает его изменённым → пересжатие произойдёт однократно, после которого маркер перезапишется (цикла не будет, т.к. новая запись сходится). Наблюдаемость через логи сохранена.
- **Старые файлы с заглушкой** (`size: null`): поведение не меняется — пропуск. Новый код заглушек не создаёт.

## Валидация на устройстве (после сборки APK)

Сценарий: новое фото → автосжатие → в логе ожидается одна строка «✅ Размер файла X записан в маркер сжатия», затем перечитывание маркера с тем же размером и `ALREADY_COMPRESSED` на следующем скане; отсутствие строк «повтор (попытка…» и «сброшен на заглушку».
