# План: сохранение исходного размера фото в EXIF-маркере

## Проблема
Сейчас EXIF-маркер `CompressPhotoFast_Compressed:quality:timestamp:size` хранит только сжатый размер (для проверки повторной обработки). Через длительное время невозможно узнать исходный размер файла и эффективность сжатия конкретного фото: `StatsTracker` хранит лишь агрегированную суточную статистику, теряемую при очистке данных.

## Решение
Расширить EXIF-маркер (EXIF UserComment) до:

```
CompressPhotoFast_Compressed:quality:timestamp:size:origSize
```

- `origSize` — исходный размер файла в байтах до сжатия, фиксированная ширина 15 с ведущими нулями (как `size`).
- Пользователь смотрит эффективность через стороннее EXIF-приложение (UserComment уже читается любым EXIF-вьюером). UI в приложении не добавляется.
- Эффективность считается внешне: `(origSize − size) / origSize × 100%`.
- Обратная совместимость: маркеры старого формата (4 поля) и заглушки парсятся как раньше.

## Изменения

### Android (`app/src/main/java/com/compressphotofast/util/`)

1. **`ExifUtil.kt`**
   - Добавить `MARKER_ORIG_SIZE_FIELD_WIDTH = 15`.
   - `CompressionMarkerInfo`: добавить `originalFileSize: Long?` (null — старый формат/заглушка).
   - `buildCompressionMarker(quality, timestamp, size, origSize)`: в фазе 1 (заглушка `size == null`) `origSize` пишется реально, т.к. известен до сжатия; `size` — нули. Фаза 2 перезаписывает только `size` (та же длина строки).
   - Парсер: разделять по `:`; ≥5 полей → читаем `origSize`; 4 поля → `originalFileSize = null`. Проверить, что нулевая заглушка `origSize` (не должна возникать, но защититься) трактуется как null.
   - Экспортировать публичную функцию чтения маркера (например `readCompressionMarker`), если текущий парсер приватный.

2. **`ImageProcessingChecker.kt`** — логика повторной обработки не меняется (использует только поле `size`); убедиться, что индексация полей после расширения не сломана (парсер позиционный — проверить все использования `split`).

3. **`ImageCompressionWorker.kt`** — передавать исходный размер в `ExifUtil` при записи маркера (уже есть `sourceSize`).

### CLI (`compressphotofast-cli/`)

4. **`src/constants.py` / `src/compression.py`** — зеркальное расширение формата маркера: та же строка с `origSize`, та же семантика записи. Сохранить семантическое соответствие Android (инвариант AGENTS.md).

### Тесты

5. **`CompressionMarkerSizeTest.kt`** (unit):
   - парсинг нового 5-полевого формата (size + origSize);
   - парсинг старого 4-полевого формата → `originalFileSize == null`;
   - заглушка фазы 1: `size` нулевой → null, `origSize` валидный;
   - запись фазы 2 не меняет длину строки и не портит `origSize`;
   - проверка повторной обработки по-прежнему работает на новом формате.
6. **`HeicInstrumentationTest.kt`** — проверки `contains("CompressPhotoFast_Compressed")` остаются валидными; проверить точный формат строки.
7. CLI-тесты — если есть тесты формата маркера, обновить аналогично.

### Документация

8. **`AGENTS.md`** (через навык `agents-updater`): обновить инвариант маркировки — формат `quality:timestamp:size:origSize`, origSize пишется в фазе 1, эффективность восстанавливается из маркера сторонним EXIF-приложением.

## Риски и edge cases

- **Повторное сжатие** файла с маркером (расхождение размера > 4 КБ): при успешном пережатии `origSize` должен обновляться на размер файла перед новым сжатием (т.е. предыдущий сжатый размер).
- **HEIC**: маркер без размера (заглушка/старый формат) — пропуск; новое поле не должно ломать HEIC-ветку записи.
- **Дрейф `saveAttributes()`**: фаза 2 не меняется, допуск 4 КБ сохраняется.
- **Сторонние редакторы**, переписывающие EXIF, могут потерять UserComment — вне нашего контроля.

## Валидация

1. `./gradlew assembleDebug`.
2. `./gradlew testDebugUnitTest` (новые тесты маркера).
3. CLI: прогнать на тестовом изображении, убедиться что UserComment содержит `origSize` и читается EXIF-вьюером.
4. Ручная проверка: сжать фото, открыть в стороннем EXIF-приложении, посчитать эффективность.
