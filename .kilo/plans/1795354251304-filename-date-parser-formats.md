# Расширение форматов дат в FileNameDateParser

## Цель

`data/FileNameDateParser.kt` (используется только `ExifDateFixUseCase.kt:151`, в CLI аналога нет) должен распознавать распространённые форматы дат в именах файлов, которые сейчас намеренно отвергаются. API `parseDateMs(displayName: String?): Long?` не меняется — меняется только покрытие.

## Принятые решения (интервью с пользователем)

1. **Day-first гибрид**: `01-02-2025` → сначала трактуем как DD-MM-YYYY; если календарно невалидно (например `12-25-2025`) — fallback на MM-DD-YYYY. Неоднозначные случаи — день первый (приложение ru).
2. **2-значные годы** (`251201`, `25-12-01`) — **не добавлять** (риск счётчиков/ID).
3. **Месяцы словами** — только английские (Jan..Dec + полные имена), включая iOS-стиль WhatsApp `Jan 1, 2025 at 12;30;45`. Русские — нет.
4. **Epoch-расширения, двоеточия, таймзоны** — добавить всё (детали ниже).

## Технические решения (защита от ложных срабатываний)

- **Day-first только с разделителями** `[-._/]` (не пробел, не слитно): слитные `01122025` и пробельные `01 02 2025` — высокий риск совпадения со счётчиками/ID, остаются нераспознанными.
- **TZ-суффикс** (`Z`, `±HH:MM`, `±HHMM`) распознаётся только когда в матче есть время и разделитель дата-время — `T` или пробел. Дефисные сигналы вида `signal-2025-01-02-03-04-05-123` не получат ложную зону. Валидация зоны: |HH| ≤ 14, MM ≤ 59.
- **Наносекунды (19 цифр) — только с известными префиксами** (`mmexport` и т.п.): 19-значные снежинки Twitter/Instagram как ns попадают в окно 1990–сейчас+1с → ложные даты. Для голого basename 19 цифр остаются null.
- **Микросекунды (16 цифр)** — и в basename, и с префиксами: 16-значные соцсетевые ID как µs дают 2128+ год → отсекаются окном валидации автоматически.
- Существующие негативные тесты `12345678.jpg`, `received_10161672603575608` (17 цифр) остаются null.

## Новый порядок шаблонов (первое совпадение по приоритету выигрывает)

1. **EPOCH_PREFIX**: `(?:mmexport|wx_camera_|snapchat-)` + 13|16|19 цифр → мс / µs (÷1000) / нс (÷1e6).
2. **Всецифровой basename**: 13 → мс, 16 → µс, 10 → с. (19 и прочие длины — null, продолжение по шаблонам ниже.)
3. **MONTH_NAME** (новый, `(?i)`): Jan..Dec / January..December с `\b`-границами:
   - `MMM D[D],? YYYY` — `Jan 1, 2025`, `Jan 01 2025`;
   - `D[D] MMM YYYY` — `01 Jan 2025`;
   - `YYYY[-_ ]MMM[-_ ]D[D]` — `2025-Jan-01`;
   - слитно `01Jan2025`;
   - опциональное время после даты: `[ T_]?(?:at )?HH[;:. _-]MM(?:[;:. _-]SS)?` — покрывает iOS `at 12;30;45` (двоеточия на FAT заменены на `;`) и обычные `12:30:45` / `12.30.45`.
4. **COMPACT_DATETIME** (как сейчас): 14 цифр, разделитель даты-времени `[_\-. T]`. Без изменений.
5. **SEPARATED_DATETIME** (год-первый, расширить): к разделителям времени МЕЖДУ H/M/S и M/S добавить `:` → `2025-01-01 12:30:45`, `2025-01-01_12:30`. Плюс опциональная TZ-группа (см. выше), применяемая только при разделителе дата-время `T`/пробел.
6. **DAY_FIRST** (новый): `(?<!\d)(\d{1,2})[-._/](\d{1,2})[-._/](19|20)\d{2}(?!\d)` + опциональное время `[ T_]?HH[:._-]MM(?:[:._-]SS)?`. Разбор: DD-MM-YYYY; невалидно → MM-DD-YYYY; обе невалидны → null. Без TZ.
7. **DATE_ONLY** (как сейчас): год-первый, 8 цифр.

Порядок критичен: год-первый и словесный — надёжнее day-first, поэтому стоят раньше; существующие шаблоны приоритетно перекрывают новые на смешанных именах.

## Разбор TZ (п. 5)

- `Z` → Calendar в UTC; `±HH:MM`/`±HHMM` → Calendar с `TimeZone.getTimeZone("GMT±HH:MM")`, затем `timeInMillis`. `isLenient = false` сохранить.
- Без TZ — локальная таймзона (текущая семантика).

## Риски

- Ложные EXIF-даты на счётчиках вида `10-11-2025`: с 4-значным годом 19/20 и валидным календарём вероятность низка; принято осознанно (решение пользователя — гибрид).
- TZ в бездвоеточном виде `±HHMM` ограничена условием «разделитель дата-время T/пробел» и валидацией |HH|≤14 — конфликт с мс-хвостами Signal исключён тестом.
- Семантика существующих имён не меняется: все текущие позитивные тесты остаются зелёными без правок ожиданий (кроме переноса `01-02-2025` из негативов в позитивы).
